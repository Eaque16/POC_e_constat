1. OBJECTIF DU PROJET
---------------------

E-Constat IA est une application de déclaration vocale d'un sinistre automobile.
L'assuré enregistre ou importe un récit audio. Le système :

1) reçoit et contrôle le fichier audio ;
2) transcrit localement le récit en français ;
3) transforme la transcription en un E-Constat JSON structuré ;
4) repère les informations critiques absentes ;
5) prépare les questions complémentaires à poser ;
6) propose prudemment des corrections pour certains noms et lieux ivoiriens.

Le flux fonctionnel est :

Microphone/fichier audio
        -> interface Gradio
        -> API FastAPI /audio/transcribe
        -> Faster-Whisper
        -> texte et segments horodatés
        -> API FastAPI /claims/extract
        -> extracteur déterministe ou Qwen/Ollama
        -> E-Constat JSON
        -> champs manquants, questions et suggestions de correction

Le traitement est conçu pour fonctionner localement. Par défaut, l'extraction
rapide ne nécessite ni service cloud ni modèle de langage actif.


2. TECHNOLOGIES ET ARCHITECTURE
-------------------------------

Langage principal : Python
Backend HTTP       : FastAPI
Serveur ASGI       : Uvicorn
Frontend           : Gradio
Validation         : Pydantic
Client HTTP        : HTTPX
Transcription      : Faster-Whisper / CTranslate2
Modèle LLM local   : Qwen 2.5 1.5B via Ollama (facultatif)
Tests              : unittest, avec pytest disponible en développement

Architecture logique :

frontend/app.py
   |
   | HTTP
   v
backend/app/main.py
   |
   +-- api/transcription.py -> services/transcription.py -> Faster-Whisper
   |
   +-- api/claims.py
          +-- services/extraction.py (rapide et déterministe)
          +-- services/ollama_client.py (analyse Qwen facultative)
          +-- services/claim_questions.py (complétude)
          +-- services/domain_lexicon.py (noms et lieux ivoiriens)
          +-- schemas/*.py (contrats Pydantic)

Le projet sépare correctement :
- la présentation dans frontend/ ;
- les routes HTTP dans backend/app/api/ ;
- les structures de données dans backend/app/schemas/ ;
- la logique métier dans backend/app/services/ ;
- les ressources IA dans ai/ ;
- les références du domaine dans data/ ;
- la vérification automatisée dans tests/.

Backend
~~~~~~~

backend/__init__.py
backend/app/__init__.py
backend/app/api/__init__.py
backend/app/schemas/__init__.py (implicite si absent selon packaging utilisé)
backend/app/services/__init__.py
  Marquent les répertoires Python comme modules/imports du projet.

backend/app/main.py
  Point d'entrée FastAPI. Crée l'application « E-Constat IA API », version
  0.1.0, branche les routes audio et claims, puis expose :
  - GET / : retourne le nom du projet et l'état running ;
  - GET /health : retourne {"status": "ok"}.

backend/app/api/transcription.py
  Implémente POST /audio/transcribe. Ce fichier :
  - contrôle le nom et l'extension ;
  - accepte WAV, MP3, M4A, OGG et WebM ;
  - lit l'upload par blocs de 1 Mio ;
  - applique une limite configurable, 25 Mio par défaut ;
  - refuse un fichier vide ou trop volumineux ;
  - écrit dans un fichier temporaire ;
  - exécute le travail bloquant dans un thread FastAPI ;
  - supprime toujours le fichier temporaire ;
  - traduit les erreurs en réponses HTTP 400, 413, 415 ou 500.

backend/app/api/claims.py
  Implémente POST /claims/extract. Ce fichier :
  - sélectionne l'extraction rapide ou Ollama ;
  - accepte aussi le choix use_llm envoyé par le frontend ;
  - revient automatiquement à l'extracteur déterministe si Ollama échoue ;
  - calcule les champs critiques manquants ;
  - génère les questions complémentaires ;
  - calcule les suggestions de correction ;
  - mesure le temps de traitement en millisecondes.

Schémas de données
~~~~~~~~~~~~~~~~~~

backend/app/schemas/claim.py
  Définit le modèle central EConstat et ses sous-modèles :

  Assure :
  - nom ;
  - prenom ;
  - telephone ;
  - numero_contrat.

  Vehicule :
  - immatriculation ;
  - marque ;
  - modele.

  Sinistre :
  - type_sinistre ;
  - date_sinistre ;
  - heure_sinistre ;
  - lieu ;
  - description ;
  - liste des degats.

  EConstat :
  - assure ;
  - vehicule ;
  - sinistre ;
  - transcription originale ;
  - informations_manquantes ;
  - confidence optionnelle, obligatoirement entre 0 et 1 si renseignée.

  Les informations absentes restent nulles. Les listes utilisent une factory
  pour éviter qu'elles soient partagées entre plusieurs objets.

backend/app/schemas/transcription.py
  Contrat de réponse de la transcription : texte, langue, probabilité de langue,
  durée et segments. Chaque segment possède un début, une fin et un texte.

backend/app/schemas/extraction.py
  Contrats de l'extraction :
  - requête avec transcription de 1 à 20 000 caractères et use_llm ;
  - suggestion de correction avec champ, valeur entendue, suggestion,
    confiance et question de confirmation ;
  - réponse avec EConstat, méthode, champs manquants, questions, corrections
    et temps de traitement.

Services métier et IA
~~~~~~~~~~~~~~~~~~~~~

backend/app/services/transcription.py
  Service Faster-Whisper. Il :
  - valide le chemin et l'extension audio ;
  - charge le modèle une seule fois grâce à lru_cache ;
  - force la transcription en français ;
  - active le filtre VAD pour les zones de parole ;
  - désactive condition_on_previous_text ;
  - emploie des hotwords et un prompt initial adaptés à la Côte d'Ivoire ;
  - transforme l'itérateur Whisper en segments horodatés ;
  - assemble les segments non vides en transcription complète ;
  - retourne langue, probabilité et durée.

backend/app/services/extraction.py
  Extracteur conservateur sans LLM. Des expressions régulières et règles
  explicites détectent :
  - prénom et nom après « je m'appelle » ou « mon nom est » ;
  - numéro de téléphone ;
  - numéro de contrat/police ;
  - immatriculation/plaque ;
  - date explicite JJ/MM/AAAA ou JJ-MM-AAAA ;
  - dates relatives « aujourd'hui » et « hier » ;
  - heure ;
  - lieu selon plusieurs formulations françaises ;
  - collision, vol ou incendie ;
  - dégâts : aile, capot, pare-chocs, phare, portière, porte, rétroviseur,
    vitre.

  Il n'invente pas les valeurs absentes et conserve la transcription complète
  comme description du sinistre.

backend/app/services/ollama_client.py
  Client d'extraction structurée pour Ollama/Qwen. Il :
  - construit le prompt français versionné ;
  - envoie une requête à /api/chat ;
  - impose le JSON Schema du modèle Pydantic ExtractedClaim ;
  - utilise temperature=0 ;
  - valide le JSON retourné ;
  - compare les données critiques avec le texte source ;
  - rejette une valeur critique non justifiée par la transcription ;
  - limite le type aux valeurs collision, vol ou incendie ;
  - ne conserve un dégât proposé que s'il apparaît dans le récit ;
  - fusionne le résultat sûr avec l'extraction déterministe ;
  - encapsule les erreurs réseau, JSON ou validation dans OllamaExtractionError.

  Par prudence, les dates et heures restent issues de l'extracteur déterministe.

backend/app/services/claim_questions.py
  Vérifie sept champs critiques et produit une question pour chacun des champs
  absents : prénom, nom, contrat, immatriculation, date, lieu et type de sinistre.

backend/app/services/domain_lexicon.py
  Charge et met en cache les lexiques ivoiriens. Il :
  - normalise accents et ponctuation pour les comparaisons ;
  - fournit à Whisper un contexte lexical ;
  - cherche la valeur la plus proche avec SequenceMatcher ;
  - utilise un seuil de 0,74 pour les lieux ;
  - utilise un seuil de 0,82 pour les noms/prénoms ;
  - propose une confirmation sans modifier silencieusement la valeur critique.

4. ENDPOINTS DE L'API
---------------------

GET /
  Réponse : {"project": "E-Constat IA", "status": "running"}

GET /health
  Réponse : {"status": "ok"}

POST /audio/transcribe
  Entrée : multipart/form-data, champ audio.
  Formats : .m4a, .mp3, .ogg, .wav, .webm.
  Sortie : texte, langue, probabilité, durée et segments horodatés.

POST /claims/extract
  Entrée JSON :
  {
    "transcription": "récit du sinistre",
    "use_llm": false
  }

  Sortie JSON :
  {
    "claim": { ... EConstat ... },
    "extraction_method": "deterministic-fast",
    "missing_fields": [],
    "questions": [],
    "correction_suggestions": [],
    "processing_time_ms": 1.23
  }

Valeurs possibles observées pour extraction_method :
- deterministic-fast ;
- ollama-hybrid ;
- deterministic-fallback.


5. MODÈLES UTILISÉS
-------------------

Faster-Whisper « small »
  Modèle de reconnaissance vocale utilisé par défaut, exécuté sur CPU en int8.
  Le téléchargement du modèle intervient au premier usage s'il n'est pas en
  cache. La langue française est imposée et le beam size vaut 3.

Qwen 2.5 1.5B
  Modèle de langage local facultatif via Ollama. Le projet référence :
  - le modèle Ollama qwen2.5:1.5b dans .env.example ;
  - un Modelfile pour un fichier GGUF instruct quantifié Q4_K_M.
  Il sert uniquement à l'extraction structurée approfondie, pas à la
  transcription.

Extracteur déterministe Python
  Ce n'est pas un modèle appris. Il repose sur des expressions régulières,
  vocabulaires et règles explicites. Il garantit une réponse rapide et fournit
  le mode de secours lorsque Qwen/Ollama n'est pas accessible.

8. SÉCURITÉ, ROBUSTESSE ET PRÉVENTION DES HALLUCINATIONS
--------------------------------------------------------

Mesures déjà implémentées :

- liste blanche des extensions audio ;
- limite d'upload configurable ;
- lecture par blocs de 1 Mio ;
- rejet des fichiers sans nom et des fichiers vides ;
- stockage temporaire, avec nettoyage même après une erreur ;
- contrat d'entrée limité à 20 000 caractères ;
- validation Pydantic de toutes les réponses publiques ;
- bornes 0..1 sur les probabilités/confiances ;
- température Qwen à zéro ;
- JSON Schema imposé à Ollama ;
- prompt interdisant l'invention ;
- vérification des valeurs critiques dans la transcription ;
- valeurs inconnues conservées à null ;
- correction des noms/lieux proposée mais jamais appliquée en silence ;
- repli automatique vers une méthode locale déterministe ;
- messages HTTP distincts pour les principales erreurs.

- chiffrement applicatif des dossiers ;
- véritable appel continu et transcription en streaming ;

- génération d'un PDF de constat officiel ;
- envoi à une compagnie d'assurance ;
- tableau de bord de gestion ;

- score global de confiance réellement calculé ;
- prise en charge complète de toutes les formulations françaises ;
- vérification sémantique complète des dates/heures proposées par le LLM.

Le README indique également que le streaming continu, l'extraction LLM et la
diarisation « viendront plus tard ». Dans le code actuel, l'extraction LLM a
déjà été ajoutée sous forme facultative et hybride ; le streaming et la
diarisation restent absents.


13. CONCLUSION
--------------

Le cœur fonctionnel est opérationnel : audio -> transcription -> extraction
structurée -> contrôle de complétude -> questions. L'architecture est modulaire,
locale et testée. La priorité donnée aux valeurs explicites, à la validation et
au repli déterministe rend le prototype prudent face aux hallucinations.

Pour passer à une application exploitable, les prochaines grandes étapes sont
la persistance en base de données, l'authentification, le dialogue multi-tours,
la production d'un constat final et la sécurisation d'un déploiement réel.
